# POST /verify

Verify the license status of a healthcare provider across multiple government data sources in a single API call.

## Endpoint

```
POST https://api.veriflowapi.com/v1/verify
```

## Request headers

| Header | Required | Value |
|---|---|---|
| `Authorization` | Yes | `Bearer YOUR_API_KEY` |
| `Content-Type` | Yes | `application/json` |

## Request body

```json
{
  "first_name": "Sarah",
  "last_name": "Chen",
  "state": "FL",
  "npi": "1234567890",
  "dob": "1975-03-15",
  "profession": "physician"
}
```

### Request parameters

| Parameter | Type | Required | Description |
|---|---|---|---|
| `first_name` | string | Yes | Provider's first name. Fuzzy matching handles minor typos and variations. |
| `last_name` | string | Yes | Provider's last name. |
| `state` | string | Yes | Two-letter US state code (e.g. `CA`, `TX`, `NY`). The state where the license was issued. |
| `npi` | string | No | 10-digit National Provider Identifier. Strongly recommended — significantly improves match accuracy. |
| `dob` | string | No | Date of birth in ISO 8601 format (`YYYY-MM-DD`). Disambiguates same-name providers and, in particular, clears false OIG exclusion matches on common names. See [OIG exclusion matching](#oig-exclusion-matching). |
| `profession` | string | No | Restrict the check to one profession, e.g. `physician`, `nurse_practitioner`, `psychologist`. See [Profession](#profession). Recommended wherever you know it: several states license every occupation from one register, so a name alone can match a different profession. |

**Note on `npi` and `dob`:** Both are optional but strongly recommended whenever available. Without them, identity resolution relies on name and state alone, which can produce false positives for common names — including false matches against the OIG exclusion list. Supplying `npi` and/or `dob` disambiguates the provider and clears same-name collisions.

### Response fields

| Field | Type | Description |
|---|---|---|
| `verified` | boolean | Top-level pass/fail. `true` if provider was found, license is active, and no OIG exclusion exists. |
| `status` | string | Current license status. See [Status Values](#status-values) below. |
| `match_confidence` | string | Strength of the identity match: `high` (matched by NPI), `medium` (exact name), `low` (name nickname/typo variant), or `null` when not found. Lower values are name-only matches — supply an `npi` for `high`. See [Identity resolution](#identity-resolution). |
| `name` | string | Provider's full name as it appears in source records. |
| `license_number` | string | State license number. |
| `profession` | string | The profession of the licence that matched, in canonical form (`physician`, `nurse_practitioner`, ...), so it is comparable across states. `null` where the state publishes no readable profession — see [Profession](#profession). |
| `professions_covered` | array | Every profession we verify in this state, as canonical values. Present on every response for a supported state, including `not_found`, so you can tell a role we never look up from a clinician who holds no licence. `null` for an unsupported state. See [Profession](#profession). |
| `license_type` | string | The licence type in the state's own wording (`Medical Doctor`, `ADV PRACTICE NURSE`, `Advanced Registered Nurse Practitioner License`). Use it to audit the `profession` classification and to see detail the canonical value flattens. |
| `state` | string | Full state name. |
| `expiry_date` | string | License expiry date in ISO 8601 format (`YYYY-MM-DD`). |
| `disciplinary_flags` | boolean | `true` if any disciplinary actions, sanctions, or malpractice findings are on record. |
| `oig_excluded` | boolean | `true` if the provider matches the HHS OIG exclusion list. A matching `npi` or `dob` confirms; a *different* `npi` or `dob` rules out a same-name stranger; a name-only match is reported conservatively (still `true`). See [OIG exclusion matching](#oig-exclusion-matching). |
| `sources_checked` | array | List of data sources checked in this request. |
| `source_live` | boolean | `true` if data was fetched live from source. `false` if served from cache. |
| `cached` | boolean | Whether this response was served from cache. |
| `cache_expires_at` | string | ISO 8601 timestamp when this cached result will be refreshed. |
| `checked_at` | string | ISO 8601 timestamp of when this verification was performed. |
| `verification_id` | string | Unique identifier for this verification. Use for audit trail and certificate retrieval. |
| `certificate_hash` | string | SHA256 hash of the signed verification certificate. |

### Status values

| Status | Description | `verified` value |
|---|---|---|
| `active` | License is current and in good standing | `true` |
| `inactive` | License exists but is not currently active | `false` |
| `suspended` | License has been temporarily suspended | `false` |
| `expired` | License has passed its expiry date | `false` |
| `revoked` | License has been permanently revoked | `false` |
| `not_found` | No matching provider found in sources checked | `false` |
| `unsupported_state` | We do not yet cover the requested state, so no license lookup was performed | `false` |
| `profession_not_covered` | The state is supported but we do not verify the profession you named there. Returned only when you send `profession`, and only where that is confirmed, so it never appears for a caller who omits the field. `verified` is `false`. Federal NPPES and OIG checks still run. |
| `source_unavailable` | The state board could not be reached, so licensure is unknown | `false` |

**`not_found` and `source_unavailable` are not the same thing,** and treating them alike is the most common integration mistake. `not_found` is an answer from the board: it holds no matching record. `source_unavailable` is the absence of an answer: the board was unreachable and we will not guess. Route the first to your normal exception workflow and the second to a retry.

### Distinguishing "no record" from "no answer"

Government license sites go down. When a state board is unreachable and we hold
no usable cached result, VeriflowAPI returns `status: "source_unavailable"` with
`verified: false`. We deliberately do **not** report `not_found` in that case,
because "the board has no record of this provider" and "we could not ask the
board" are opposite conclusions for a credentialing decision.

```json
{
  "verified": false,
  "status": "source_unavailable",
  "match_confidence": null,
  "state": "New York",
  "sources_checked": ["NPPES", "OIG", "NY Office of the Professions"],
  "source_live": false,
  "checked_at": "2026-09-07T08:15:00Z"
}
```

Recommended handling:

- **Retry** after a short delay rather than treating the provider as unlicensed.
- **Do not cache** a `source_unavailable` result as a verification outcome.
- **Route to manual review** if it persists across retries.
- Check [the status page](https://veriflowapi.com/status.html) to see which
  sources are currently degraded, and note that federal signals (`oig_excluded`
  and NPPES identity) in the same response are still valid.

Before returning `source_unavailable`, we first serve the most recent cached
result for that provider if one exists, flagged with `source_live: false` so you
can see the data is not fresh.

## Profession

Most states run a separate board per profession, but several publish **one register covering every
licensed occupation** — Illinois and Connecticut among them. In those states a name on its own can
match an entirely different occupation, so every verification is restricted to healthcare licences
and, when you ask for one, to the profession you name.

### Values

`physician`, `physician_assistant`, `nurse_practitioner`, `registered_nurse`, `practical_nurse`,
`nurse_anesthetist`, `nurse_midwife`, `nursing_assistant`, `psychologist`, `social_worker`,
`counselor`, `marriage_family_therapist`, `physical_therapist`, `occupational_therapist`,
`speech_language_pathologist`, `audiologist`, `dentist`, `pharmacist`, `optometrist`, `podiatrist`,
`chiropractor`, `midwife`, `acupuncturist`, `dietitian`, `respiratory_therapist`,
`athletic_trainer`, `emergency_medical`, `massage_therapist`.

An unrecognised value is rejected with `422`, so a typo fails loudly rather than silently widening
the search.

### How the filter behaves

Sending `profession` **narrows** a check; it never widens one.

- A licence in the profession you named is returned.
- A licence confidently in a *different* profession is excluded — this is what stops a nurse's
  active licence answering a question about a physician.
- If the state does not verify the profession you named at all, you get `profession_not_covered`
  instead of `not_found`, before any board is asked. An LCSW in Massachusetts (physicians only)
  is the canonical case: previously `not_found`, which read as "holds no licence".
- A licence we cannot classify is still returned, ranked after any exact match, with
  `profession: null` and the state's raw wording in `license_type`. An unmapped vocabulary costs
  precision, never coverage.

### When `profession` comes back null

`profession` is `null` when the state does not publish a readable profession. Colorado is the
clearest case: DORA's public dataset ships only a coded prefix (`RN`, `AP`, `APE`) with no
dictionary, so we return the raw code in `license_type` and leave `profession` empty rather than
guess. Read `license_type` in that case.

Omitting `profession` is safe. Non-healthcare licences are excluded either way — the filter only
adds precision *within* healthcare. You will never see `profession_not_covered` without sending
`profession`; without it we cannot know which role you meant, and a `not_found` is a real lookup
miss. Read `professions_covered` on that response to tell the two apart.

### Two states where absence is not proof

Colorado publishes only coded licence prefixes with no dictionary, and New York searches every
profession the state licenses, which we have not fully enumerated. In both, `professions_covered`
lists what we have confirmed, and a profession outside that list returns `not_found` after a real
lookup rather than `profession_not_covered`, because we cannot be certain it is uncovered.

## Identity resolution

Before verifying license status, VeriflowAPI resolves provider identity by matching the last name exactly, then the first name. First-name matching accepts:

- Nicknames where one form is a prefix of the other (e.g. "Bob" vs "Robert")
- Middle initials included or omitted
- Hyphenated last names
- Minor typos in submitted names

It deliberately does **not** match genuinely different given names that merely look alike (e.g. "John" vs "Joan", "Satish" vs "Satinder"). Those return `not_found` rather than a false match — a wrong-person confirmation is worse than a miss.

Every successful match reports a `match_confidence`:

| Confidence | Meaning |
|---|---|
| `high` | Matched on the `npi` — exact identity. |
| `medium` | Exact first + last name, no NPI. |
| `low` | Name nickname/typo variant, no NPI. |

Because name-only matching is inherently ambiguous for common names, **supply an `npi` whenever available** for `high`-confidence, exact-identity verification. When ambiguity cannot be resolved, we return `not_found`.

## OIG exclusion matching

The OIG LEIE (List of Excluded Individuals/Entities) is matched by name and then narrowed by the identifiers you supply. Because roughly 90% of LEIE records carry no NPI, name is the primary key — so a common name can collide with an excluded stranger. VeriflowAPI uses `npi` and `dob` to resolve those collisions:

- **A matching `npi`** confirms the exclusion — the strongest signal, an exact identity match.
- **A different `npi` or `dob`** on a same-name record rules it out as a different person, so `oig_excluded` returns `false`.
- **A name-only match** — no identifier supplied, or none on the LEIE record — is reported conservatively as `oig_excluded: true`. We would rather surface a possible match for your review than silently clear a real exclusion.

To avoid false positives on common names, **supply `dob` (and `npi` where you have it) on every check.** Most LEIE records carry a date of birth, so a `dob` clears a same-name stranger even when the record has no NPI.

## Sandbox &amp; testing

Test keys (`vf_test_`) run against the **same data and coverage as production** — an ordinary provider returns exactly what a live key would, including `unsupported_state` for states we don't yet cover. This makes your sandbox integration faithful to production.

To exercise every branch of your integration deterministically, use **reserved test last names** (case-insensitive) on a `vf_test_` key. They work in any state and force a specific outcome, similar to test card numbers:

| Last name | Result |
|---|---|
| `Sandbox_Active` | `verified: true`, `status: "active"` |
| `Sandbox_Expired` | `status: "expired"`, not verified |
| `Sandbox_Suspended` | `status: "suspended"`, not verified, disciplinary flag |
| `Sandbox_Revoked` | `status: "revoked"`, not verified, disciplinary flag |
| `Sandbox_NotFound` | `status: "not_found"`, not verified (also simulates a name mismatch) |
| `Sandbox_Excluded` | `oig_excluded: true`, not verified |
| `Sandbox_Disciplined` | `verified: true`, `disciplinary_flags: true` |

To simulate `unsupported_state`, query any state we don't cover (e.g. `OH`) with an ordinary name. These triggers apply **only to test keys** — on a live key they are treated as ordinary names.

## Caching policy

To maximize uptime and minimize response time, VeriflowAPI caches responses according to the following TTL policy:

| Data type | Cache TTL |
|---|---|
| State license status (active/inactive/suspended/expired/revoked) | 24 hours |
| NPPES identity (name, NPI) | 24 hours |
| OIG exclusion status | 12 hours |

When a response is served from cache, `cached` will be `true` and `source_live` will be `false`. The `cache_expires_at` field tells you exactly when fresh data will be fetched.

This caching policy means VeriflowAPI maintains 99.9% uptime even when government source sites experience downtime.

## Code examples

### Python

```python
import requests

def verify_provider(api_key, first_name, last_name, state, npi=None, dob=None):
    payload = {
        "first_name": first_name,
        "last_name": last_name,
        "state": state
    }
    if npi:
        payload["npi"] = npi
    if dob:
        payload["dob"] = dob

    response = requests.post(
        "https://api.veriflowapi.com/v1/verify",
        headers={
            "Authorization": f"Bearer {api_key}",
            "Content-Type": "application/json"
        },
        json=payload
    )

    if response.status_code == 200:
        return response.json()
    else:
        raise Exception(f"API error {response.status_code}: {response.json()}")
```

### Node.js

```javascript
const axios = require('axios');

async function verifyProvider(apiKey, { firstName, lastName, state, npi, dob }) {
  const response = await axios.post(
    'https://api.veriflowapi.com/v1/verify',
    {
      first_name: firstName,
      last_name: lastName,
      state,
      ...(npi && { npi }),
      ...(dob && { dob })
    },
    {
      headers: {
        'Authorization': `Bearer ${apiKey}`,
        'Content-Type': 'application/json'
      }
    }
  );

  return response.data;
}
```

### Ruby

```ruby
require 'net/http'
require 'json'
require 'uri'

def verify_provider(api_key, first_name:, last_name:, state:, npi: nil, dob: nil)
  uri = URI('https://api.veriflowapi.com/v1/verify')
  http = Net::HTTP.new(uri.host, uri.port)
  http.use_ssl = true

  request = Net::HTTP::Post.new(uri)
  request['Authorization'] = "Bearer #{api_key}"
  request['Content-Type'] = 'application/json'
  request.body = {
    first_name: first_name,
    last_name: last_name,
    state: state,
    npi: npi,
    dob: dob
  }.compact.to_json

  response = http.request(request)
  JSON.parse(response.body)
end
```
